## Objetivos

Al terminar esta lección podrás:

- Distinguir qué problema resuelve cada técnica: el prompt, el comportamiento; el RAG, el conocimiento; el ajuste fino, el comportamiento que el prompt no consigue.
- Medir si un modelo "sabe" algo sin documentación, y qué hace cuando no lo sabe.
- Clasificar los fallos de un sistema con RAG para saber qué técnica los arreglaría.
- Formular, con datos, si merece la pena ajustar un modelo.

## Teoría

### Tres técnicas, tres problemas

Cuando un sistema con LLM no da lo que necesitas, hay tres palancas, y cada una arregla una cosa distinta:

- **El prompt** cambia lo que el modelo hace con lo que ya sabe: el formato, las reglas, el tono. Es barato y rápido de probar: el módulo 2.
- **El RAG** le da el conocimiento que no tiene: tus documentos, en el momento de responder. Se actualiza cambiando los documentos y permite citar la fuente: el módulo 3.
- **El ajuste fino** (*fine-tuning*) cambia el modelo: sus pesos. Sirve para que haga mejor y de forma más consistente una tarea concreta (un formato, un estilo, seguir unas reglas), o para que un modelo pequeño haga lo que antes necesitaba uno grande. Es lo más caro: datos de entrenamiento, cómputo, evaluación y mantenimiento.

Una idea muy extendida es que el ajuste fino sirve para "enseñarle al modelo tu documentación". Funciona mal para eso: cuesta mucho meter hechos nuevos en los pesos de forma fiable, cada cambio en la documentación obliga a reentrenar y el modelo no puede citar de dónde sale lo que dice. Hay estudios que lo comparan con el RAG para inyectar conocimiento, y el RAG gana (en Para profundizar). Si vienes de backend: el conocimiento es como los datos de una base de datos, y el comportamiento, como el código. No compilas los datos en el binario.

### El orden de las preguntas

1. ¿Lo arregla un prompt mejor? Pruébalo primero: cuesta minutos.
2. ¿Le falta conocimiento? RAG, o meter el documento entero en el contexto si cabe (lección 3.01).
3. ¿Tiene el conocimiento delante y aun así se equivoca? Es un problema de comportamiento: un modelo mayor, o ajustar uno pequeño para la tarea.

Y antes de responder ninguna, mide dónde falla. Sin eso, se elige técnica por moda.

## Mide y depura

### Sin documentación, no saben nada de la empresa

De las 42 preguntas con respuesta en la documentación, el 7B acierta 2 sin ella, y el 1,5B, 1. No es que sean malos modelos: los runbooks de una empresa ficticia no están en sus datos de entrenamiento, igual que no lo estarían los de la tuya. El conocimiento lo pone el RAG: con él, 38 y 32.

Lo que cambia entre los dos es qué hacen cuando no saben. El 7B se abstiene en la mayoría (inventa en 10 de 42) y acierta 14 de las 16 preguntas que no deben responderse. El 1,5B inventa en 32 de 42. Un modelo pequeño sin documentación es una fuente de respuestas falsas con buena redacción.

Para este sistema, ajustar un modelo para que "aprenda la documentación" sería el camino equivocado: habría que convertir los 29 documentos del corpus en datos de entrenamiento, reentrenar con cada cambio y renunciar a las citas. El RAG ya resuelve el conocimiento.

### Con RAG, el modelo pequeño falla por comportamiento

El 1,5B con RAG acierta 40 de 58, frente a 52. Las 12 que pierde se reparten así:

- **6 en las que respondió cuando tocaba abstenerse.** El prompt tiene reglas para eso (lección 4.06), las mismas que sigue el 7B; el pequeño no las sigue.
- **4 en las que respondió mal teniendo la respuesta en el contexto.**
- **2 en las que se abstuvo teniendo la respuesta delante.**

Ninguna se debe a la recuperación: en todas, el contexto era el mismo que el del 7B, que acertó. Mejorar la búsqueda no arreglaría nada. Lo que falla es cómo el modelo pequeño usa el contexto y sigue las reglas: un problema de comportamiento.

### La hipótesis del módulo

El prompt ya se intentó: es el mismo que funciona con el 7B. Quedan dos opciones: usar siempre el 7B, que tarda 11,5 s de mediana por respuesta en esta CPU, o enseñar al 1,5B, que tarda 2,6 s, a comportarse como el 7B en esta tarea. Eso último es un ajuste fino, y se puede hacer con las respuestas del 7B como ejemplos (destilación). Es la hipótesis que siguen las lecciones 05 y 06: ¿cuántas de esas 12 recupera un 1,5B ajustado, y a qué coste?

## Errores frecuentes

**Ajustar un modelo para meterle tu documentación.** Es caro, se queda viejo con cada cambio y no cita. Para conocimiento, RAG.

**Decidir la técnica sin saber dónde falla el sistema.** Si el fallo es de recuperación, ni un modelo mejor ni un ajuste fino lo arreglan. Clasifica los fallos primero, como en el módulo 4.

**Dar por bueno lo que el modelo "sabe".** Sin documentación, el 7B dio una explicación correcta en general y equivocada para esta empresa (la anatomía). Lo que suena bien no es lo que dice tu documentación.

**Saltarse el prompt.** Es la palanca más barata. Pero si el mismo prompt funciona con un modelo mayor y no con el pequeño, el problema ya no es el prompt.

**Olvidar el coste de mantener un modelo ajustado.** Hay que reentrenarlo cuando cambie la tarea o salga un modelo base mejor, y evaluarlo cada vez.

### Anatomía de un error: la respuesta correcta para cualquier empresa menos esta

Sin documentación, el 7B respondió así a una pregunta del dataset:

```text
«¿Qué significa el error invalid_grant al iniciar sesión con Google?»
→ El error "invalid_grant" indica que el código de autorización o el token de acceso
  proporcionado no es válido o ha expirado.
```

**Cómo leerlo.** La respuesta es correcta como explicación general de OAuth. Pero la documentación de la plataforma dice otra cosa: en este sistema, ese error aparece cuando el secreto de cliente de OAuth ha caducado. Quien estuviera de guardia buscaría un token de usuario expirado y no el secreto del servicio, que es lo que hay que renovar.

**Causa.** El modelo responde con lo que vio en su entrenamiento: miles de páginas sobre OAuth en general, ninguna sobre esta empresa. No tiene forma de distinguir "lo que suele pasar" de "lo que pasa aquí", y el prompt le pedía abstenerse si no sabía. Para él, sí sabía.

**Solución.** Lo que ya hace el asistente: RAG, citas y abstención cuando la respuesta no está en los fragmentos. Con la documentación delante, el sistema vigente responde la causa concreta. Y la lección para decidir técnica: un modelo que "sabe" mucho en general no sabe nada de tu sistema, y ajustarlo con tus documentos le daría un conocimiento que caduca con el próximo cambio.

## Para profundizar

- Ovadia et al., [Fine-Tuning or Retrieval? Comparing Knowledge Injection in LLMs](https://arxiv.org/abs/2312.05934) (2023): el RAG gana al ajuste fino para meter conocimiento nuevo.
- Lewis et al., [Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks](https://arxiv.org/abs/2005.11401) (2020): el artículo que dio nombre al RAG.
- Hu et al., [LoRA: Low-Rank Adaptation of Large Language Models](https://arxiv.org/abs/2106.09685) (2021): el ajuste fino eficiente de la lección 05.
- [PEFT, de Hugging Face](https://huggingface.co/docs/peft/index): la librería de referencia para LoRA y otros ajustes finos eficientes.
