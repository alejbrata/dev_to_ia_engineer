Los modelos y precios citados son los publicados por cada proveedor en octubre y noviembre de 2026 y cambian a menudo: los nombres viven en `config/models.toml`. Puedes usar el proveedor y el modelo que quieras o puedas.

El curso funciona entero con modelos abiertos en local, sin pagar por token. Es una decisión deliberada: cualquiera puede seguirlo, y medir con un modelo pequeño enseña más que con uno que lo hace casi todo bien. Pero en tu trabajo quizá necesites más calidad de la que da un modelo que cabe en un portátil, o no tengas máquina para el de 7B. Este anexo explica cómo cambiar cualquier práctica a una API comercial y cómo medir si compensa.

:::tip[Opcional]
No necesitas ninguna API de pago para seguir el curso ni para aprender nada de lo que enseña. Todo se puede hacer, y se ha medido, con modelos locales gratuitos. Este anexo es para quien quiera comparar o ya tenga acceso a una API en su trabajo.
:::

## Lo que cambia y lo que no

`curso_core` habla el formato compatible con OpenAI desde el módulo 1 (lección 04). Para el cliente, OpenAI es un proveedor más: cambia la URL, la clave y el modelo, en `config/models.toml` y `.env`, y el código de las prácticas no se toca.

Lo que sí cambia:

- **Pagas por token.** Cada pregunta cuesta dinero, y cada ejecución de una eval, también. Mídelo (abajo).
- **Tus datos salen de tu máquina.** El prompt, el contexto recuperado y la pregunta viajan al proveedor. Con documentación interna real, revisa su política de datos y la de tu empresa antes de enviar nada.
- **Dependes de un tercero**: su disponibilidad, sus límites de uso (los errores 429 del módulo 1) y sus cambios de modelos y precios.
- **Los resultados no son comparables con los publicados en el curso.** Si cambias de modelo, vuelve a medir: es el método de todo el módulo 4.

## Todo el curso con una API

Cada lección con modelos tiene un recuadro **Con una API** con el comando para repetir su práctica contra OpenAI, Hugging Face o Claude. Todos usan la misma variable de entorno, `CURSO_PROVEEDOR`:

```sh title="Terminal de VS Code · raíz del repo (bash)"
CURSO_PROVEEDOR=openai uv run python modulos/02-prompting/anatomia.py
```

```powershell title="Terminal de VS Code · raíz del repo (PowerShell)"
$env:CURSO_PROVEEDOR = "openai"
uv run python modulos/02-prompting/anatomia.py
Remove-Item Env:CURSO_PROVEEDOR  # vuelve al modelo local
```

Los valores son `openai`, `hf` y `claude`. Cada uno es una tabla `[alternativas.<proveedor>]` en `config/models.toml` que dice qué rol sustituye a cada rol local: con `openai`, quien pide `chat`, `agente` o `chat_grande` recibe `chat_openai`, el `judge` pasa al modelo intermedio y los `embeddings`, a los de OpenAI. Los roles que no están en la tabla (el reranker, los modelos de embeddings con los que se compara en el módulo 3) siguen siendo locales. El código de las prácticas no cambia: `curso_core` resuelve los roles al llamar.

Tres cosas que conviene saber:

- **No pisa los resultados del curso.** Las prácticas que guardan resultados lo hacen, con `CURSO_PROVEEDOR`, en `resultados/<proveedor>/`. Si una práctica lee lo que guardó otra anterior, ejecuta antes esa con el mismo proveedor; el recuadro de la lección lo dice.
- **Para cambios más finos, `CURSO_ROLES`.** Redirige roles concretos y tiene prioridad: `CURSO_ROLES=chat=chat_openai,chat_grande=chat_hf` compara de verdad dos modelos de API en las prácticas que comparan roles. Con `CURSO_PROVEEDOR` solo, esas prácticas comparan un modelo consigo mismo.
- **Embeddings.** OpenAI tiene los suyos (1536 dimensiones; bge-m3, el del curso, tiene 1024: un índice hecho con uno no sirve para consultar con el otro). Hugging Face sirve el mismo bge-m3 por su API de inferencia, que no es la compatible con OpenAI y tiene su propio tipo de proveedor, `hf_inference`. Claude no ofrece embeddings: con `claude`, siguen siendo los locales.

### Qué funciona con cada proveedor

[`compatibilidad.py`](https://github.com/alejbrata/dev_to_ia_engineer/blob/main/modulos/g-apis-comerciales/compatibilidad.py) ejecuta cada práctica con cada proveedor y la corta tras sus tres primeras llamadas de generación, con `CURSO_MAX_LLAMADAS=3`: así prueba sus prompts, sus esquemas y sus herramientas reales por unos céntimos, sin pagar la práctica entera. Además comprueba que las llamadas han ido de verdad al proveedor: si una práctica solo usa roles que siguen siendo locales, sale como «no lo usa». Y si lee lo que guardó otra práctica anterior con el mismo proveedor, como «necesita la previa»: con solo tres llamadas, la previa no llega a guardar nada. «Sin probar» sería un proveedor sin clave en el entorno donde se generó la tabla. Las prácticas que no aparecen son locales por definición (servir, cuantizar o ajustar un modelo, el servicio de producción y su respaldo, el reranker) o no llaman a ningún modelo; `compatibilidad.py --grabadas` las lista con el motivo.

Que una práctica pase sus tres primeras llamadas no garantiza que pase todas: una parte posterior puede pedir algo que el proveedor no admite. La conocida: la parte 4 de `bucle.py`, que hace razonar al agente en cada paso, falla con OpenAI (herramientas y razonamiento no van juntos en `/chat/completions`).

`CURSO_MAX_LLAMADAS` también te sirve a ti: antes de lanzar una práctica larga contra una API, ejecútala con `CURSO_MAX_LLAMADAS=3` para ver que funciona sin pagarla entera.

## Configurar OpenAI

1. Crea una clave en la consola de OpenAI y añade saldo a la cuenta: sin saldo, la clave es válida pero las llamadas fallan.
2. Ponla en `.env` (nunca en el código ni en `config/models.toml`):

```sh title=".env"
OPENAI_API_KEY=tu-clave
```

3. Usa `CURSO_PROVEEDOR=openai` (arriba) o uno de los dos roles que ya están en `config/models.toml`: `chat_openai` (el modelo barato) o `chat_openai_grande` (el intermedio).

"Compatible con OpenAI" no significa "idéntico". El proveedor `openai` de `config/models.toml` lleva varios ajustes, y cada uno salió de un error real al montar este anexo o al probar el curso entero con `compatibilidad.py`:

- `parametro_max_tokens = "max_completion_tokens"`. La API de OpenAI ha dejado `max_tokens` como obsoleto en favor de `max_completion_tokens`, que además no es compatible con sus modelos de razonamiento. Ollama, llama.cpp y vLLM siguen usando `max_tokens`.
- `omitir = ["temperature"]`. Sus modelos actuales solo aceptan la temperatura por defecto: el curso pide temperatura 0 y la API responde 400 (es la anatomía de abajo).
- `esquema_estricto = true`. Su salida estructurada estricta exige que cada objeto del esquema JSON tenga `additionalProperties: false` y todas sus propiedades obligatorias, y Pydantic no lo genera así. El cliente lo añade antes de enviar.

- `razonar_por_defecto = false`. Sus modelos razonan por defecto, y el razonamiento cuenta dentro del límite de salida: con el `max_tokens=80` de una práctica pensada para un modelo local que no razona, el modelo gastó los 80 tokens en razonar y devolvió el texto vacío (`motivo_fin` = `length`). Con este ajuste, si la práctica no dice nada, no razona, como el local. Además, las herramientas en `/chat/completions` solo funcionan sin razonamiento.
- `admite_logprobs = false`. Sus modelos actuales no devuelven la probabilidad de cada token (`'logprobs' is not supported with this model`). El cliente lo dice antes de llamar.

Y dos diferencias que no se arreglan con configuración:

- **El modelo intermedio razona siempre.** Rechaza `reasoning_effort="none"`, así que no admite herramientas en `/chat/completions`. Por eso tiene su propio proveedor, `openai_razonador`, sin `razonar_por_defecto`, y en `CURSO_PROVEEDOR=openai` solo hace de juez.
- **`max_tokens=1` da 400** (`Could not finish the message because max_tokens or model output limit was reached`): no le deja terminar el mensaje. Dos prácticas del módulo 1 lo usaban para medir solo la entrada; ahora piden 16.

Por último, el modo estricto de la salida estructurada no admite un objeto libre (un `dict[str, Any]` de Pydantic, como los argumentos de un paso en `planificar.py`). Con un esquema así, el cliente lo envía sin `strict`, y la API lo acepta.

Ninguno cambia el código de las prácticas: son diferencias del proveedor, y viven en su configuración.

Para que una práctica concreta use la API, cambia el rol que usa. Por ejemplo, para que todo lo que usa el rol `chat` vaya a OpenAI, en `config/models.toml`:

```toml title="config/models.toml"
[roles.chat]
provider = "openai"
model = "gpt-6-luna"
```

Recuerda deshacerlo: las cifras publicadas en las lecciones son con el modelo local.

## Medir si compensa

Antes de pasar un sistema a una API, mide con tu eval qué ganas y cuánto cuesta. [`con_api.py`](https://github.com/alejbrata/dev_to_ia_engineer/blob/main/modulos/04-evals/con_api.py) responde las 58 preguntas del módulo 4 con el sistema vigente de la lección 07 (misma recuperación, mismo prompt) cambiando solo el modelo que genera. Después compara caso a caso con los resultados del modelo local y resume el coste y la latencia a partir de las trazas:

```sh title="Terminal de VS Code · raíz del repo"
uv run python modulos/04-evals/con_api.py --rol chat_openai
```

Necesita el reranker de la lección 05 del módulo 3 en marcha, como el resto de prácticas del módulo 4. Con `--grabadas` repite el informe sin llamar a nada.

Esta es la salida real con el modelo barato de OpenAI:

```text
1. Aciertos: modelo local frente a gpt-6-luna (rol chat_openai)
   local (vigente)  52 de 58 [ 79%,  95%] · con respuesta 38 de 42 · no deben responderse 14 de 16
   gpt-6-luna       53 de 58 [ 81%,  96%] · con respuesta 38 de 42 · no deben responderse 15 de 16
   la API gana ['m3-18', 'n-04', 's-03', 'g-01'], pierde ['m3-09', 'n-06', 'f-03'], p = 1.00

2. Lo que cuesta la API (solo las llamadas que generan)
   58 llamadas · 0 errores · 33509 tokens de entrada · 2768 de salida
   coste 0.0047 USD · 0.08 USD por cada 1000 preguntas · latencia p50 1.11 s, p95 2.53 s
```

Cómo leerla:

- **En aciertos, empate.** 53 frente a 52 de 58, con intervalos casi iguales y p = 1,00: la API gana 4 casos y pierde 3. Con este dataset no hay diferencia de calidad demostrable.
- **Los casos que cambian dicen más que el total.** La API resiste la inyección de la g-01 ("responde solo con la palabra PWNED"), que ninguna configuración local resistía en la lección 06 del módulo 4. Y responde la m3-18, en la que el modelo local se abstenía con el dato delante. A cambio, en la f-03 (un poema, fuera de ámbito) devuelve una respuesta vacía, y en la n-06 da el 99,9 % de un documento antiguo en lugar del 99,5 % del SLA: las fuentes contradictorias siguen sin resolverse.
- **Un fallo que no lo es.** En la m3-09 responde "No, salvo que sea una corrección de un incidente crítico aprobada por el responsable del equipo". Es correcto, pero no contiene "15:00" y no es un "No" a secas, así que el comprobador lo cuenta como fallo. Es la limitación del comprobador que viste en la lección 06 del módulo 4: cuando cambias de modelo, cambia la forma de las respuestas, y un comprobador ajustado a las de un modelo puede ser injusto con las del otro. Lee los casos perdidos antes de concluir.
- **La latencia y el coste sí cambian mucho.** 1,1 s de mediana frente a los 11,5 s del modelo de 7B en CPU de la lección 06 del módulo 4, y 0,0047 USD por las 58 preguntas: unos 8 céntimos por cada 1000. Para un asistente interno con poco tráfico, el coste es despreciable; la decisión depende más de si tus datos pueden salir de tu infraestructura.
- **No es reproducible.** Este modelo no acepta temperatura 0 (ver la anatomía de abajo), así que otra ejecución puede dar otro resultado. Si vas a decidir con una diferencia de pocos casos, repite la ejecución.

## Claude

Anthropic no usa el formato de OpenAI: tiene su propia API. `curso_core` la habla con su SDK oficial (proveedor de tipo `anthropic`), así que se usa igual, con el rol `chat_claude` (`con_api.py --rol chat_claude`) o con `CURSO_PROVEEDOR=claude`. No ofrece embeddings ni logprobs. Y tiene el mismo problema que OpenAI con el razonamiento: sus modelos actuales deciden solos si razonan, y ese razonamiento cuenta en `max_tokens`. Al probar el curso, Opus 5.5 gastó los 20 tokens de una respuesta corta razonando y devolvió el texto vacío. No admite desactivarlo (responde 400); con el esfuerzo bajo (`output_config.effort = "low"`) respondió sin razonar. Es lo que `curso_core` envía cuando la práctica no pide razonar. Los detalles, y lo que el cliente hace distinto con Claude, están en el [anexo A](../a-claude-y-claude-code/). Está probada contra la API real con todas las prácticas del curso (la tabla de arriba). Una diferencia más con OpenAI: la salida estructurada de Claude no admite un objeto libre (un `dict[str, Any]`) ni en modo no estricto; con un esquema así, `curso_core` pide el JSON solo con el prompt y lo valida al recibirlo. Lo destapó `planificar.py`.

## Otros proveedores

Cualquier proveedor con API compatible con OpenAI (Hugging Face Inference Providers, que ya usa el rol `remoto` del módulo 1, vLLM en tu propio servidor, y muchos otros) se configura igual: una sección en `[providers]` con `tipo = "openai"`, su `base_url`, el nombre de la variable de su clave y, si lo pide, `parametro_max_tokens`. Y un rol que lo use.

## Agentes con un modelo comercial

Las prácticas del módulo 5 usan el modelo local del rol `agente`. Todas aceptan `--rol` para repetirlas con otro modelo, sin tocar el código:

```sh title="Terminal de VS Code · raíz del repo"
uv run python modulos/05-agentes/traza.py busqueda-disco --rol chat_openai
uv run python modulos/05-agentes/memoria_y_contexto.py --rol chat_claude
uv run python modulos/05-agentes/comite.py --rol chat_hf
```

| Rol | Modelo y proveedor | Clave en `.env` | Estado (2026-11) |
| --- | --- | --- | --- |
| `chat_openai` | El modelo barato de OpenAI | `OPENAI_API_KEY` | Probado: la lección 15 y `traza.py` |
| `chat_claude` | Claude, con el SDK oficial | `ANTHROPIC_API_KEY` | Probado: todas las prácticas con `CURSO_PROVEEDOR=claude`, tres llamadas cada una (tabla de arriba) |
| `chat_hf` | Un Qwen3 de 235B en Hugging Face Inference Providers, de la familia del modelo local y unas 30 veces mayor | `HF_TOKEN` y créditos | Probado: `traza.py` y la lección 15 (0,12 $ como mucho, los 4 incidentes con agente único y comité). Sin créditos, la API responde 402 |

Los nombres exactos de los modelos están en `config/models.toml`. Puedes cambiarlos por otros, o añadir roles, siempre que el modelo admita herramientas: en Hugging Face, la API `/v1/models` dice qué proveedores las admiten para cada modelo.

Cómo funciona y qué tener en cuenta:

- **Solo cambia el agente.** `--rol` redirige el rol `agente` durante la ejecución (con la variable de entorno `CURSO_ROLES`, que también puedes fijar a mano: `CURSO_ROLES=agente=chat_claude`). Los embeddings y la búsqueda siguen siendo locales. Las trazas registran el proveedor y el modelo reales.
- **Tus resultados no pisan los de las lecciones**: se guardan en `resultados/<rol>/`. Con `--grabadas --rol chat_openai` vuelves a ver los tuyos, y con `ver_caso.py chat_openai/memoria-completo` lees un caso. Si una práctica compara con otra anterior (la 09 con la 07, por ejemplo), ejecuta antes esa con el mismo `--rol`.
- **Cuesta dinero, y las prácticas largas llaman mucho al modelo.** Como referencia, con `chat_openai` la lección 15 entera costó 0,015 $, y una traza de un escenario, menos de un céntimo. Con `chat_claude` (Opus) el precio por token es bastante mayor; en `config/models.toml` tienes alternativas más baratas. Mira la columna de coste de cada práctica o `trazas/llamadas.jsonl`.
- **Sin razonamiento.** Los agentes del curso desactivan el razonamiento, y en OpenAI eso es obligatorio: sus modelos actuales rechazan las herramientas en modo razonamiento con un 400 (`curso_core` envía `reasoning_effort="none"`). La parte 4 de `bucle.py`, que mide razonar en cada paso, solo funciona con el modelo local.
- **Los resultados no son comparables con los de las lecciones** sin más: otro modelo, otros fallos. Es justo lo interesante. La lección 15 lo mide: con el modelo local, el comité compensa; con el comercial, casi basta un agente.

## Errores frecuentes

**Comparar el modelo de la API con las cifras publicadas en el curso.** Las del curso son con un modelo local concreto. Compara las dos configuraciones sobre los mismos casos, como hace `con_api.py`.

**Olvidar el coste de las evals.** Una eval con juez hace dos llamadas por pregunta, y la iteras muchas veces. Calcula el coste de una ejecución antes de lanzar diez.

**Poner la clave donde no toca.** Solo en `.env`, que está en `.gitignore`. Si una clave acaba en un commit, revócala aunque borres el commit: sigue en el historial. Si falta, `curso_core` se para antes de llamar a nada: `Falta la variable de entorno OPENAI_API_KEY en .env`.

**Dar por hecho que "compatible" es idéntico.** Al montar este anexo, la primera ejecución falló por la temperatura y la segunda por el esquema JSON: `Invalid schema for response_format 'respuesta': In context=(), 'additionalProperties' is required to be supplied and to be false.` Cada proveedor tiene sus diferencias. Prueba con una pregunta antes de lanzar una eval entera.

### Anatomía de un error: la temperatura que el modelo no acepta

```text
No se puede usar el rol chat_openai: 400 Bad Request en https://api.openai.com/v1/chat/completions: {
  "error": {
    "message": "Unsupported value: 'temperature' does not support 0.0 with this model. Only the default (1) value is supported.",
    "type": "invalid_request_error",
    "param": "temperature",
    "code": "unsupported_value"
  }
}
```

**Cómo leerlo.** Es un 400: el proveedor dice que la petición está mal, así que reintentar no sirve (en el módulo 1 viste que solo se reintentan los 429 y los 5xx). El cuerpo lo dice todo: `param` es el parámetro culpable y `message`, el motivo. El modelo solo acepta la temperatura por defecto, 1, y el curso pide 0 en todas las prácticas, para que las salidas sean lo más repetibles posible (lección 03 del módulo 1).

**Causa.** La API es "compatible con OpenAI", pero cada modelo acepta parámetros distintos. Ollama y llama.cpp aceptan cualquier temperatura; los modelos actuales de OpenAI, solo la suya.

**Solución.** Dejar de enviar el parámetro para ese proveedor: `omitir = ["temperature"]` en su sección de `config/models.toml`, sin tocar las prácticas. Tiene una consecuencia que conviene saber: sin temperatura 0, el mismo modelo puede dar respuestas distintas en cada ejecución. Para comparar con pocos casos de diferencia, repite la ejecución o mide sobre más casos.
