## Objetivos

Al terminar esta lección podrás:

- Traducir un grafo de estado propio a LangGraph: `StateGraph`, nodos, aristas condicionales, checkpointer e `interrupt()`.
- Comprobar con datos que el framework no cambia las decisiones del agente, y medir lo que añade en tiempo y en dependencias.
- Reconocer las diferencias de comportamiento que importan: cómo se reanuda una interrupción, qué pasa con los campos que el estado no tiene y qué se reconstruye al leer un checkpoint.
- Decidir con criterio entre un motor propio y un framework para tu caso.

## Teoría

### Qué es LangGraph

LangGraph es una librería de código abierto, del equipo de LangChain, para construir agentes como grafos de estado. Tiene las mismas piezas que el motor de la lección 05, con otros nombres:

| Motor propio (`grafo.py`) | LangGraph |
| --- | --- |
| `Grafo(EstadoGuardia, inicio=...)` | `StateGraph(EstadoGuardia)` y `add_edge(START, ...)` |
| `g.nodo(nombre, funcion)` | `g.add_node(nombre, funcion)` |
| `g.arista(a, b)` | `g.add_edge(a, b)` |
| `g.arista_condicional(a, condicion, destinos)` | `g.add_conditional_edges(a, condicion, mapa)` |
| `FIN` | `END` |
| `Checkpoints(carpeta)`, un JSONL por hilo | un *checkpointer*: `InMemorySaver`, `SqliteSaver`, `PostgresSaver` |
| `hilo="..."` | `{"configurable": {"thread_id": "..."}}` |
| `interrumpir_antes={"abrir"}` y `cambios` al reanudar | `interrupt(valor)` dentro de un nodo y `Command(resume=...)` |
| `MAX_PASOS` | `recursion_limit` en la configuración |

Si has hecho la lección 05, ya sabes lo que hace cada pieza. Eso es lo que se gana construyendo el motor antes que usar el framework: el framework deja de ser una caja negra.

### Lo que LangGraph hace distinto

No todo es cambiar nombres. Hay diferencias de diseño que cambian cómo se comporta el sistema:

- **La interrupción va dentro de un nodo.** Se llama a `interrupt(valor)`: el grafo se para, guarda el checkpoint y devuelve `valor` a quien lo ejecuta. Al reanudar con `Command(resume=respuesta)`, `interrupt()` devuelve `respuesta`. Pero el nodo **se ejecuta otra vez desde el principio**: todo lo que haya antes de `interrupt()` se repite. Por eso la aprobación es un nodo propio (`aprobar`), sin nada caro ni con efectos antes de la llamada. LangGraph también permite paradas fijas al compilar (`interrupt_before`), como el motor propio, pero su documentación recomienda `interrupt()` para la aprobación humana.
- **Reductores.** Cada campo del estado puede tener una función que decide cómo se combinan las actualizaciones: sustituir (lo de por defecto, como el motor propio) o, por ejemplo, añadir a una lista. Sirve para que varios nodos que se ejecutan en paralelo escriban en el mismo campo sin pisarse.
- **Pasos en paralelo.** Si de un nodo salen varias aristas, los nodos de destino se ejecutan en el mismo paso, a la vez. El motor propio ejecuta un nodo cada vez.
- **Persistencia intercambiable.** El mismo grafo guarda en memoria, en SQLite o en Postgres cambiando una línea. Si un nodo falla en un paso con varios nodos en paralelo, LangGraph guarda lo que hicieron los que sí terminaron (*pending writes*) y no los repite al reanudar.
- **Lo que viene alrededor**: varios modos de streaming (por nodo, por token), historial de checkpoints para volver a un estado anterior, políticas de reintento por nodo y un ecosistema de herramientas de observabilidad y despliegue, algunas comerciales.

### Lo que cuesta

Un framework se paga en dependencias, en versiones y en abstracciones. Instalar `langgraph` y su checkpointer de SQLite añadió **24 paquetes** al entorno del curso (`langchain-core`, `langsmith`, `ormsgpack`, `zstandard`...). Cada uno es código de terceros que actualizar y vigilar. Y la API cambia: algo que hoy funciona con un aviso puede bloquearse en la siguiente versión. Lo vas a ver en la anatomía.

## Práctica

[`grafo_langgraph.py`](https://github.com/alejbrata/dev_to_ia_engineer/blob/main/modulos/05-agentes/grafo_langgraph.py) monta el grafo de guardia con LangGraph. Los nodos y la condición son los de `grafo_guardia.py`, sin cambiar una línea. Solo se añade el nodo de aprobación:

```python
def aprobar(e: EstadoGuardia) -> dict:
    respuesta = interrupt({"servicio": e.servicio, "decision": e.decision.model_dump()})
    cambios = {"aprobada": respuesta["aprobada"]}
    if "decision" in respuesta:  # la persona ha corregido la propuesta
        cambios["decision"] = Decision.model_validate(respuesta["decision"])
    return cambios


def construir(nodos: NodosGuardia, checkpointer):
    g = StateGraph(EstadoGuardia)
    g.add_node("clasificar", nodos.clasificar)
    g.add_node("recoger", nodos.recoger)
    g.add_node("decidir", nodos.decidir)
    g.add_node("aprobar", aprobar)
    g.add_node("abrir", nodos.abrir)
    g.add_edge(START, "clasificar")
    g.add_edge("clasificar", "recoger")
    g.add_edge("recoger", "decidir")
    g.add_conditional_edges(
        "decidir", tras_decidir, {"decidir": "decidir", "abrir": "aprobar", FIN: END}
    )
    g.add_edge("aprobar", "abrir")
    g.add_edge("abrir", END)
    return g.compile(checkpointer=checkpointer)
```

La condición `tras_decidir` devuelve los nombres del motor propio (`"abrir"`, `FIN`); el mapa de `add_conditional_edges` los traduce a los de este grafo. Para ejecutarlo, [`con_langgraph.py`](https://github.com/alejbrata/dev_to_ia_engineer/blob/main/modulos/05-agentes/con_langgraph.py) usa `stream` con `stream_mode="updates"`, que devuelve lo que cambia cada nodo según termina. Así mide el tiempo por nodo y detecta la interrupción (llega como `__interrupt__`):

```python
for actualizacion in grafo.stream(entrada, config, stream_mode="updates"):
    for nodo, valor in actualizacion.items():
        if nodo == "__interrupt__":
            return pasos, valor[0].value       # lo que interrupt() enseña a la persona
        ...
# más tarde, cuando la persona decide:
grafo.stream(Command(resume={"aprobada": True}), config, stream_mode="updates")
```

Ejecuta lo mismo que `grafos.py` de la lección 05: los 9 escenarios aprobando todo, la caída a mitad de `decidir` y la comparación. ## Mide y depura

### Lo mismo, hasta el último token

LangGraph y el motor propio aciertan los mismos 4 escenarios, fallan los mismos 5 por los mismos motivos y gastan exactamente los mismos 9951 tokens en 18 llamadas. Es la comprobación más importante de la lección: **cambiar de motor no cambia lo que decide el agente**. Si al migrar a un framework cambian tus resultados, no es el framework, es que algo de tu lógica cambió por el camino, y tus evals deberían cazarlo.

La caída también se comporta igual: `get_state(config).next` dice `['decidir']`, y al reanudar con `stream(None, config)` se ejecuta `decidir` sin repetir `clasificar` ni `recoger`.

### Milisegundos frente a segundos

La parte 5 mide el motor solo: unos 0,7 ms por paso el propio (con su JSONL) y unos 3 ms LangGraph (con SQLite). Cuatro veces más, y da igual: un paso que llama al modelo tarda decenas de segundos en esta máquina. El motor es menos de una diezmilésima del tiempo. Estos números cambian de una ejecución a otra (repitiendo con el modelo ocupado en otra cosa salieron 1,2 y 4,7 ms), así que fíjate en el orden de magnitud, no en la cifra. No elijas motor por su velocidad: elige por lo que te da y lo que te cuesta mantenerlo.

### El estado que vuelve como diccionario

La última línea de la parte 2: `get_state(...).values es un dict, no un EstadoGuardia`. Dentro del grafo, cada nodo recibe el estado como modelo de Pydantic; fuera, lo que devuelven `invoke` y `get_state` es un diccionario. Si escribes `resultado.decision`, falla con `AttributeError`. `con_langgraph.py` lo vuelve a convertir con `EstadoGuardia.model_validate(valores)`.

### Qué valida cada motor

Una prueba sin modelo, con nodos falsos que devuelven datos incorrectos, saca dos diferencias:

- **Un valor del tipo equivocado** (un nodo devuelve `servicio="pago"`, que no es uno de los cinco servicios): **los dos motores fallan** con `ValidationError` antes del siguiente nodo, porque los dos reconstruyen el estado con Pydantic.
- **Un campo que el estado no tiene** (un nodo devuelve `campo_inventado`): el motor propio falla (`'recoger' devolvió campos que el estado no tiene`); **LangGraph lo descarta sin avisar** y el grafo termina como si nada. Una errata en el nombre de un campo es un dato que se pierde en silencio.

## Errores frecuentes

**Trabajo caro antes de `interrupt()`.** El nodo se repite entero al reanudar. Si llamas al modelo y luego a `interrupt()` en el mismo nodo, la llamada se repite. Pon la interrupción en un nodo propio, o al principio del nodo.

**Erratas en las claves que devuelve un nodo.** LangGraph ignora las claves que no están en el estado. Si un campo no se actualiza y no sabes por qué, revisa el nombre exacto. Un test que ejecute el grafo con nodos falsos lo caza.

**Tratar el resultado como el modelo de Pydantic.** `invoke` y `get_state(...).values` devuelven un diccionario. Conviértelo si quieres tipos.

**Olvidar el `thread_id`.** Con checkpointer, cada ejecución necesita su hilo. Si reutilizas el mismo para dos alertas, la segunda continúa el estado de la primera.

**Usar `InMemorySaver` en producción.** Desaparece con el proceso: la aprobación que esperaba desde anoche se pierde con el primer reinicio.

### Anatomía de un error: el aviso que será un error

La primera ejecución de `con_langgraph.py` empezó con esta línea, antes de cualquier salida del script:

```text
Deserializing unregistered type workflow.Decision from checkpoint. This will be blocked in a future version. Set LANGGRAPH_STRICT_MSGPACK=true to block now, or add to allowed_msgpack_modules to allow explicitly: [('workflow', 'Decision')]
```

**Cómo leerlo.** Al leer un checkpoint (*deserializing*), LangGraph se encontró un objeto de un tipo que nadie ha registrado: `Decision`, del módulo `workflow`, la decisión que guarda el nodo `decidir` en el estado. Hoy lo reconstruye y avisa una vez. El aviso dice que en una versión futura lo bloqueará, y da las dos salidas: activar ya el modo estricto, o registrar el tipo en `allowed_msgpack_modules`.

**Causa.** El checkpointer guarda el estado en binario (msgpack), con el tipo de cada objeto, y al leerlo reconstruye ese tipo. Reconstruir cualquier tipo que diga un fichero es peligroso: el propio código de LangGraph advierte de que quien pueda escribir en la base de datos de checkpoints podría llegar a ejecutar código al deserializar. Es el mismo problema que la deserialización de objetos en Java, que ha dado más de un susto en servidores de aplicaciones. Por eso LangGraph está pasando a una lista de tipos permitidos.

**Solución.** Declarar los tipos propios que se guardan en el estado al crear el checkpointer:

```python
serde = JsonPlusSerializer(allowed_msgpack_modules=[("workflow", "Decision")])
SqliteSaver(sqlite3.connect(ruta, check_same_thread=False), serde=serde)
```

Con eso el aviso desaparece y el resultado es idéntico (lo comprobamos con nodos falsos: la decisión vuelve como `Decision`, con la misma severidad). Es lo que hace ya `con_langgraph.py`. Y la lección de fondo es la de la anatomía anterior: un checkpoint es un dato persistido, y su formato es un contrato, tanto con tu código como con la versión del framework. Fija la versión en el lockfile, lee los avisos, que suelen anunciar el siguiente error, y prueba a reanudar ejecuciones antiguas antes de actualizar.

## Para profundizar

- LangGraph, [Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api): estado, reductores, nodos y aristas.
- LangGraph, [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) y [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence): `interrupt()`, `Command(resume=...)`, checkpointers e hilos.
- Malewicz et al., [Pregel: a system for large-scale graph processing](https://doi.org/10.1145/1807167.1807184) (2010). El modelo de pasos sincronizados en el que se inspira el motor de ejecución de LangGraph.
- OWASP, [Deserialization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Deserialization_Cheat_Sheet.html). Por qué deserializar tipos arbitrarios es peligroso, con ejemplos en Java y Python.
